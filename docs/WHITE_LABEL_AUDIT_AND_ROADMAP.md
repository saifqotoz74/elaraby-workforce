## 1. Executive Summary & Brutal Truth Audit

تم تحويل المنصة هندسياً من تطبيق أحادي (Monolithic Single-Tenant) خاص بشركة العربي إلى **منصة قوى عاملة مرنة ومتعددة المستأجرين (Multi-Tenant White-Label Workforce Platform)**.

### الوضع الراهن بدقة (The State Today):
* **كود العميل (Flutter Mobile App):** مكتمل ومعزول بنسبة **100%**. الألوان، اللوجو، شاشات الخدمات، البطاقات السريعة، الخط الساخن، واستراتيجيات الهوية (رقم قومي، إقامة خليجية، كود موظف) أصبحت تعمل ديناميكياً بناءً على إعدادات الـ Tenant.
* **كود الخادم وقاعدة البيانات (Node.js & PostgreSQL):** مكتمل بنسبة **100%**. جدول `tenants` موجود، حقول `tenant_id` مفهرسة ومفروضة في كل الجداول، والـ API يمرر ويفحص الـ `tenantId` في جميع الطلبات وجلسات الـ JWT والـ Rate Limiter.
* **الاختبارات الآلية:** **0 أعطال** عبر 237 اختبار Flutter و 24 حزمة اختبارات Jest / Node.js.

### الركيزة الأولى: استراتيجية نشر التطبيق على المتاجر (Store Distribution Strategy)

هناك مساران تجاريان متباينان في صناعة الساس (SaaS)، ويجب عليك حسم اختيارك بينهما:

#### المسار (أ): نموذج التطبيق الموحد الحاوي (Single Container App)
* **المثال العالمي:** مثل `Slack` أو `Microsoft Teams` أو `Workday` أو `SAP SuccessFactors`.
* **كيف يعمل:** 
  - تطبيق واحد فقط على متجر Google Play و Apple App Store باسم محايد (مثلاً: `Workforce Connect` أو `PR Connect`).
  - الموظف يقوم بتحميل التطبيق لأول مرة.
  - أول شاشة تطلب من الموظف: إما "إدخال كود شركتك" أو يتم اكتشاف الشركة تلقائياً من خلال إيميله الوظيفي (`user@elsewedy.com` -> يعرف فوراً أنه السويدي).
  - بمجرد التحقق، يتحول التطبيق فورياً لألوان وشعار وقواعد هوية شركته.
* **ما ينقص هذا المسار حالياً:**
  1. تغيير اسم التطبيق في ملفات `AndroidManifest.xml` و `Info.plist` من "العربي جروب" إلى الاسم التجاري المحايد.
  2. تغيير أيقونة التطبيق على المتجر (`ic_launcher`) لتكون أيقونة المنصة وليس لوجو شركة بعينها.
  3. تفعيل شاشة `CompanyCodeModal` لتكون أول شاشة إجبارية للتحقق من كود المؤسسة للعملاء الجدد، أو فحص الـ Domain.

#### المسار (ب): نموذج التطبيقات المنفصلة لكل شركة (Dedicated Branded Apps)
* **المثال العالمي:** مثل تطبيقات البنوك وشركات الطيران المستقلة.
* **كيف يعمل:**
  - شركة العربي لديها تطبيق باسم "العربي كونكت" بأيقونته في المتجر.
  - شركة السويدي لديها تطبيق باسم "السويدي كونكت" بأيقونته في المتجر.
  - شركة أرامكس لديها تطبيق باسم "أرامكس قوى عاملة" في المتجر.
* **ما ينقص هذا المسار حالياً:**
  1. **إعداد Flutter Flavors:**
     - إضافة flavors في `pubspec.yaml` و `android/app/build.gradle` و `ios/Runner.xcodeproj`.
     - بناء الحزم بأوامر: `flutter build appbundle --flavor elsewedy` و `flutter build ipa --flavor elaraby`.
  2. **حسابات المتاجر (Apple & Google Developer Accounts):**
     - تتطلب حسابات مطورين باسم كل شركة أو حساب شركة الساس مع تفويض (D-U-N-S Number).
  3. **CI/CD Pipeline:**
     - بناء 10 أو 15 تطبيقا يدوياً لكل تحديث مستحيل بشرياً؛ يلزم إعداد Fastlane مع GitHub Actions لنشر التحديثات لجميع العملاء بضغطة زر.

### الركيزة الثانية: عزل مفاتيح بوابات الـ SMS والـ Push Notifications

* **الوضع الحالي:**
  - مزودات الرسائل النصية (Vodafone, Cequens, Twilio) تقرأ الـ API Keys واسم المرسل الافتراضي من ملف البيئة الموحد `server/.env`.
* **الواقع العملي عند بيع الخدمة:**
  - كل شركة تشتري الخدمة تريد أن تصل رسائل التحقق (OTP) للموظف باسم شركتها:
    - موظف العربي تصله الرسالة من: **ELARABY**
    - موظف السويدي تصله الرسالة من: **ELSEWEDY**
    - عميل في السعودية يريد استخدام مزود محلي مثل **Unifonic** أو **STC**.
* **ما ينقص:**
  - إضافة حقل مشفر `sms_config` (AES-256) في جدول `tenants` يحتوي على المزود المفضل، الـ API Key، والـ Sender ID الخاص بكل شركة، أو استخدام نظام AWS Secrets Manager.

### الركيزة الثالثة: لوحة تحكم السوبر أدمن (Platform Super-Admin & Tenant Provisioning)

* **الوضع الحالي:**
  - لوحة التحكم الإدارية الحالية (`server/admin`) هي **Tenant Admin Dashboard** (أي لمدير الموارد البشرية لشركة واحدة يدير موظفيها، إجازاتهم، ومرتباتهم).
* **ما ينقص:**
  - بوابة إدارة المنصة **Platform Super-Admin Portal** التي تخصك أنت (مالك الساس):
    1. **معالج إضافة عميل جديد (Tenant Onboarding Wizard):** إدخال اسم الشركة، الرابط، رفع اللوجو والألوان، تحديد عدد تراخيص الموظفين، وتفعيل/تعطيل الموديولات.
    2. **محرك الفواتير والاشتراكات (Billing & Subscriptions):** تاريخ تجديد الاشتراك، وتعطيل وصول الشركة تلقائياً عند انتهاء العقد.
    3. **لوحة الإحصائيات المركزية (Global System Analytics):** إجمالي عدد الشركات المشتركة، إجمالي الموظفين النشطين، ومعدل استهلاك السيرفر.

### الركيزة الرابعة: أمان وعزل قواعد البيانات للمؤسسات الحساسة (Enterprise Data Isolation)

* **الوضع الحالي:**
  - النظام يستخدم نموذج **Shared Database, Shared Schema with Discriminator Column (`tenant_id`)**. هذا النموذج معتمد ومستخدم في كبرى شركات الساس العالمية (مثل Jira و HubSpot و Shopify).
* **ما ينقص للمؤسسات الكبرى فائقة الحساسية (بنوك، جهات سيادية، قطاع صحي):**
  1. **PostgreSQL Row-Level Security (RLS):**
     - تفعيل سياسات الأمان على مستوى محرك Postgres نفسه:
       ```sql
       CREATE POLICY tenant_isolation_policy ON employees
       FOR ALL TO workforce_app
       USING (tenant_id = current_setting('app.current_tenant_id'));
       ```
     - هذا يضمن 100% أنه حتى لو حدث خطأ بشري من مبرمج ونسي كتابة `WHERE tenant_id = ...`، لن تخرج أي بيانات خاصة بشركة أخرى إطلاقاً.
  2. **Database-per-Tenant Option:**
     - إمكانية تشغيل نسخة معزولة بالكامل (Isolated DB & Redis) للشركات الضخمة التي تشترط ذلك تعاقدياً.

### الركيزة الخامسة: تخزين الأصول السحابية (CDN & Dynamic Logo Caching)

* **الوضع الحالي:**
  - اللوجو المحلي الافتراضي مسجل كـ Asset ثابت، مع دعم قراءة الـ URL إذا تم توفيره.
* **ما ينقص:**
  - رفع لوجوهات وتصاميم الشركات على Storage سحابي معتمد (AWS S3 / Cloudflare R2).
  - استخدام مكتبة تخزين مؤقت على الموبايل (`cached_network_image`) تضمن حفظ اللوجو على هاتف الموظف فور تحميله أول مرة ليعمل التطبيق بكفاءة كاملة حتى في وضع عدم الاتصال (Offline-First).

## 4. ما يتبقى فقط خارج نطاق الكود (Commercial & Legal Setup)

2. **حسابات مطوري Apple و Google Play:** لرفع تطبيق `PR Connect` الموحد على المتاجر.
3. **عقود واتفاقيات مستوى الخدمة (SLA & B2B Contracts):** لبيع اشتراكات سنوية أو شهرية للشركات.
